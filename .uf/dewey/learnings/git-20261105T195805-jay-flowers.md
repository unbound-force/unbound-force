git fetch from a URL (rather than a configured remote name) writes the fetched tip to FETCH_HEAD only — no remote-tracking ref is created or updated. git status never reads FETCH_HEAD; it compares HEAD against the branch's configured upstream tracking ref (refs/remotes/<remote>/<branch>), which cannot exist when branch.<name>.remote holds a URL. Any divergence or fast-forward gate that fetches from a push target that may be a URL must compare explicitly against the fetched tip: `git rev-list --left-right --count HEAD...FETCH_HEAD` prints "<local-only>\t<remote-only>"; a nonzero remote-only count means the push will be rejected as non-fast-forward. Relying on `git status` after a URL fetch silently disables the gate. Observed in /uf.address-feedback Section 4.4 (PR #955, feedback item 3): the fetch targeted HEAD_REMOTE, which Section 1.2.1 explicitly allows to be a URL, so the git status divergence check could never see the fetched state.
