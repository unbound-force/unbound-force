uf_unleash_detect_resume returns a false negative for spec_review whenever the feature dir's tasks.md has unstaged-only checkbox edits — the normal state of an OpenSpec pipeline mid-implementation (observed on branch opsx/split-host-resolution-failure-classes, 2026-11-02). Root cause: defaultGitExec in .opencode/lib/uf-workflow-types.ts applies String.prototype.trim() to every git command's output, which strips the leading space of the porcelain status line " M openspec/changes/<name>/tasks.md"; porcelainEntryPath in .opencode/plugins/uf-workflow/index.ts then runs line.slice(3) on the trimmed "M openspec/..." string and misparses the path (reading "penspec/..." instead of "openspec/..."), so specArtifactsDirty reports the feature directory dirty even though tasks.md checkbox edits are exactly the case the check explicitly excludes. The unit suite (unleash-resume.test.ts) cannot catch this because its fake GitExec returns the porcelain fixture untrimmed while production always trims. Symptom: step_statuses.spec_review false with resume_from "spec_review" even when an approving specs artifact exists under .uf/artifacts/dispatch/, its recorded input_context.head_sha is an ancestor-or-equal of HEAD, and git status --porcelain -- <feature_dir> shows tasks.md as the only entry. A spec-review re-dispatch can never clear the false negative because the dirty check runs regardless of artifact recency — the pipeline would loop forever on resume. Workaround: verify the freshness legs directly (parse the artifact, run git merge-base --is-ancestor <head_sha> HEAD, run the porcelain status and confirm tasks.md is the only entry), then trust the approving artifact plus get_progress completed_steps and continue the pipeline instead of re-dispatching the council. A follow-up change should fix the parsing — either stop trimming porcelain output in the exec path or make specArtifactsDirty re-derive the XY prefix before porcelainEntryPath slices — and extend the fake-exec tests to trim output like production.
