## Why

Two `/uf.address-feedback 159` runs on `unbound-force/dewey#159` (15 inline findings + 3 body = 18 items, head `f221569`, review `5820364580`) ended mid-walkthrough without addressing any finding. Nothing was committed, pushed, or replied to and all 15 threads remain open.

Run 1 (`ses_e424917c7ffeWZUP1N92ZZAGCp`) worked items 1–12 and stopped at item 12; run 2 (`ses_e41c29f64ffeyaQ2Nb6jZnYRLc`) stopped around items 7–9. For item 12 the agent wrote its classification, Tier 2 panel outcome, and recommendation, then wrote the `question` tool call as plain text in its reply:

```
<invoke name="question"><parameter name="questions">[{"question": "Item 12 of 18 — [LOW] … Decide:", …}]</parameter></invoke>
```

No tool call was made, so no question was raised. The auto-question plugin had nothing to answer and no human was prompted; the turn ended and the session sat idle. The failure is silent — from outside it looks like normal completion.

The primary fix is out-of-scope for this repo: `jflowers/opencode-supervisor#65` (supervisor detects an idle turn whose last assistant message contains a tool call written as text and re-prompts the agent to make the real call) and `jflowers/gh-hud#9` (flag idle-waiting runs, don't record as success). Per issue comment on #1013, what remains for this change is a small, low-risk tightening: make the wording in `.opencode/commands/uf.address-feedback.md` say plainly at each per-item decision to call the `question` tool. It is not the fix, but it reduces the model's chance of emitting pseudo-XML instead of a tool call.
