## Why

On finalization failure paths, the compact result's `errors`
array is capped at 5 strings of 256 characters
(`SUMMARY_LIMITS.errors`, `SUMMARY_LIMITS.errorChars` in
`.opencode/plugins/review-dispatch/index.ts`). The cap destroys
diagnostic data three ways:

- `formatValidationError` (`.opencode/lib/reviewer-manifest.ts`)
  composes every Zod issue of a rejected input into one
  `"; "`-joined string, so the structural-failure error passes
  256 characters at roughly three issues. The cap cuts it
  mid-string; the sort inside `formatValidationError` makes the
  cut deterministic but still lossy — the tail issues are gone.
- `validatePayloadSemantics` returns one short string per
  violation and can produce dozens (per-finding and per-run
  checks over payloads of up to 512 findings and 64 runs). The
  5-entry cap drops the trailing entries.
- Unlike findings, advisories, proposals, and warnings, errors
  have no durable home on failure paths: `artifact_path` is
  `null` because no artifact was written, and
  `read_dispatch_artifact` has no `errors` section. Whatever the
  preview drops is unrecoverable.

RD-FR-051 recorded the observability caps as an accepted risk
with the narrow read tool as the remedy, and RD-FR-058
(`full-lesson-proposals`) later removed mid-string cuts for
proposals because the persisted artifact made the preview safely
lossy. Errors never received either remedy: they are the payload
of exactly the paths where nothing is persisted.

@uf-divisor flagged this as MEDIUM (sre) on PR #1004 (review
comment r4530799607): "on failure paths the compact result's
errors cap loses unrecoverable data". Identical code ships in
the scaffold mirror, so the fix lands in both.

Part of epic unbound-force/unbound-force#1060 (Release plan:
v0.22.0 — reliable unattended review & feedback), Tier 2;
tracked under the v0.22.0 milestone. An unattended run whose
finalization fails must be diagnosable after the fact from
durable state, not from whatever survived a 1,280-byte preview.

Fixes #1039.

## What Changes

- **Whole-or-absent error preview.** The compact finalization
  result (`finalize_review_dispatch` and `consolidate_dispatch`
  with provenance) never shortens an error entry.
  `SUMMARY_LIMITS.errorChars` is removed. The 5-entry `errors`
  count cap stays, and errors join the post-assembly byte
  budget: after proposals are exhausted, trailing errors are
  dropped whole and flagged `errors_truncated: true`. This is
  the RD-FR-058 present-whole-or-absent pattern applied to
  errors.
- **Durable failure record.** Every failed
  `finalize_review_dispatch` — structural rejection, semantic
  rejection, or persistence failure — best-effort writes a
  `review-dispatch-failure` artifact to
  `.uf/artifacts/dispatch/<correlation-id>.failure.json`
  carrying the complete `errors` array verbatim. The record
  reuses the Hero Interface Contract envelope shape and the
  atomic publish discipline of success artifacts (temp file,
  link, 0o750 directory, no overwrite; EEXIST mints a fresh
  record correlation id). When the dispatch correlation id is
  unusable (structural rejection of a garbage input), a fresh
  one is minted; the payload records the dispatch correlation
  separately when it differs.
- **Failure record surfaced in the result.** The compact result
  gains one key, `failure_record`, either `null` or
  `{ correlation_id, path }`, inserted immediately after
  `artifact_path` so host truncation of the tail cannot lose
  it. The key-order contract of RD-FR-051 is amended
  accordingly.
- **`read_dispatch_artifact` section `errors`.** A new section
  reads a failure record by its correlation id and returns the
  full errors array. A dispatch with only a success artifact
  reports `not_found`; a missing or invalid record fails closed
  with the existing error codes.
- **Schema registry.** A hand-authored
  `schemas/review-dispatch-failure/v1.0.0.schema.json` declares
  the record payload, mirrored to `.uf/schemas/` and
  `internal/scaffold/assets/uf/schemas/` and registered in the
  `internal/schemas` fixture tests.
- **Prose.** The `consolidate_dispatch` tool description's
  errors-cap sentence and the `read_dispatch_artifact`
  description's section list are updated to match.
- **Scaffold mirror.** Every edited `.opencode/` and schema
  file is copied byte-identical under
  `internal/scaffold/assets/`.

## Impact

- **Live plugin**: `.opencode/plugins/review-dispatch/index.ts`
  — `SUMMARY_LIMITS`, `buildCompactFinalization`,
  `FinalizeReviewDispatchResult`, `finalizeReviewDispatch`
  failure paths, the failure-record writer, the
  `read_dispatch_artifact` section enum and handler, and two
  tool descriptions.
- **Shared lib**: `.opencode/lib/reviewer-manifest.ts` is not
  functionally changed (`formatValidationError` keeps composing
  the complete string — completeness is the point); it is
  re-mirrored only if touched.
- **Schema registry**: `schemas/review-dispatch-failure/v1.0.0.schema.json`
  (new), `.uf/schemas/review-dispatch-failure/` (new mirror),
  `internal/schemas/ci_test.go` (hand-authored list).
- **Scaffold mirror**: every edited `.opencode/` and `uf/schemas/`
  file copied byte-identical under `internal/scaffold/assets/`;
  the scaffold asset list in `internal/scaffold/scaffold_test.go`
  gains the new schema path.
- **Tests**: vitest — `summary-retrieval.test.ts` (cap
  semantics, key order), `finalize-review-dispatch.test.ts` and
  `finalize-error-boundaries.test.ts` (failure record on all
  three failure paths, record-write failure degradation),
  `read-dispatch-artifact.test.ts` (`errors` section),
  `consolidate-dispatch.test.ts` (end-to-end failure path);
  Go — schema fixture tests and scaffold mirror drift tests.
- **Out of scope**: `dispatch_status` (session observability,
  tmpdir-scoped) and the commands' workflow prose beyond the
  two tool descriptions; `formatValidationError`'s composition
  itself.
- **CI replication**: `make check`.
- **Documentation impact**: CHANGELOG.md entry. The tool
  description text is user-facing (`uf init` deploys the
  mirrored plugin) — in-repo documentation issue to be filed
  per the documentation gate.

## Constitution Alignment

Assessed against the Unbound Force org constitution (v1.4.0 —
six active principles).

### I. Autonomous Collaboration

**Assessment**: PASS

A failed finalization now leaves a self-describing artifact
(producer identity, artifact type, correlation id, timestamp)
that any consumer can interpret without the producing session.
The compact result references it by path and id, so recovery
does not require the producer to still be alive.

### II. Composability First

**Assessment**: PASS

The change stays inside the review-dispatch plugin. The
failure record reuses the existing Hero Interface Contract
envelope and the existing artifact directory; no new runtime
coupling. The uf-workflow resume consumer already ignores
foreign `artifact_type` values fail-open, so the new record
type cannot disturb resume detection.

### III. Observable Quality

**Assessment**: PASS

Damage stays visible and now recoverable: a dropped preview
entry is flagged by `errors_truncated`, and the complete errors
are machine-readably persisted with provenance (branch, commit,
correlation, timestamp) and a JSON Schema in the registry.

### IV. Testability

**Assessment**: PASS

The error projection, budget loop, and failure-record writer
are pure or dependency-injected functions over the existing
`FinalizationDependencies` (filesystem, clock, UUID), unit
testable in isolation; the reader section is tested against
fixture records. No external service is required.

### V. Security by Default

**Assessment**: PASS

The failure record is written through the same atomic,
0o750-directory, no-overwrite discipline as success artifacts.
Its payload schema bounds every string, so untrusted input that
reaches a structural rejection cannot inflate the record
unboundedly; the sanity bounds sit above the natural
composition ceilings and fail closed rather than truncating.

### VI. Deterministic Execution

**Assessment**: PASS

The completeness guarantee is enforced in tool code, not
command prose. The only prose changes correct two tool
descriptions to match the enforced behavior; no mechanical
steps are added to commands.
